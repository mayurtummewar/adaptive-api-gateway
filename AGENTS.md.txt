# Development Instructions

## Project Overview

This repository contains the final-year Computer Engineering project
**AI-Powered API Security Gateway for E-commerce Applications**.

The primary research focus is an AI-based API traffic anomaly detector that
helps APISIX make adaptive security decisions. The e-commerce application
provides realistic traffic for development, testing, and model evaluation.

## Current Architecture

- **Frontend:** React with Vite under `frontend/`
- **Backend:** Python/FastAPI service roles under `backend/`, deployed as
  identity, catalog, and commerce containers
- **Database:** PostgreSQL
- **API gateway:** Apache APISIX with etcd
- **AI security engine:** Python/FastAPI with a PyTorch autoencoder under
  `ai-engine/`
- **Local orchestration:** Docker Compose

The frontend provides product browsing, search, local signup/login, a
user-owned bag, checkout, and order history. The service roles share the
existing PostgreSQL database through SQLAlchemy. APISIX routes each domain to
its own service and the Vite development proxy points only at the gateway.

## Development Rules

1. Inspect existing code before modifying it.
2. Make small, testable changes and preserve existing user work.
3. Do not claim a feature is complete without testing it.
4. Reuse existing patterns and avoid unnecessary dependencies or architecture.
5. Ask before making major architectural changes or deleting existing code.
6. Keep documentation aligned with the actual implementation status.
7. Explain important technical decisions briefly and clearly.
8. Surface errors explicitly; do not hide failures behind silent fallbacks.

## Target Request Flow

The intended flow is:

```text
React/Vite frontend
        |
        v
Apache APISIX gateway
   |          |          |
   v          v          v
Identity   Catalog    Commerce
   \          |          /
          PostgreSQL
                ^
                |
         AI security engine
```

APISIX should remain the public API entry point. The backend and AI engine
should remain independent services. The AI engine must not contain e-commerce
business logic; it should evaluate request features and return explainable
security information.

## Security Policy

The eventual gateway policy must support:

- `ALLOW` for acceptable traffic
- `RATE LIMIT` for suspicious or high-frequency traffic that should be slowed
- `BLOCK` for traffic that exceeds the blocking policy

The AI service now uses a supervised Random Forest trained from the labeled
traffic dataset. It returns `ALLOW` below probability `0.5`, `RATE LIMIT`
from `0.5` through below `0.9`, and `BLOCK` at `0.9` or above. The previous
autoencoder remains in the artifacts and evaluation scripts for comparison,
but is not the active scorer because it produced false positives on normal
traffic.

The AI engine is containerized in Compose and exposes its local health/score
service on `http://localhost:8001`. APISIX calls the AI service during request
rewriting and enforces `RATE LIMIT` as HTTP 429 and `BLOCK` as HTTP 403. The
classifier must be validated on broader traffic before being treated as
production-ready. APISIX also applies a real `limit-count` policy of 60
requests per minute per client address; this gateway counter is independent
from the AI feature payload.

## Implementation Order

Work through these phases in small, tested increments:

1. Keep the documentation and repository status accurate.
2. Inspect and stabilize the React/Vite frontend.
3. Implement the FastAPI backend with PostgreSQL.
4. Add product schemas, seed data, and product endpoints.
5. Connect the frontend to the backend through APISIX.
6. Add cart and order endpoints and complete the e-commerce flow.
7. Containerize and integrate the AI engine.
8. Implement and test the `ALLOW`/`RATE LIMIT`/`BLOCK` policy.
9. Add focused tests and local end-to-end validation.
10. Prepare the Docker Compose deployment for AWS.

The current local scope is products, cart, orders, and local email/password
authentication. Third-party identity providers and payment providers are
intentionally out of scope.

## Local Development

Development is performed on Windows with PowerShell, Docker Desktop, and
WSL2. The configured local gateway and APISIX Admin API ports are:

- Gateway: `http://localhost:9081`
- APISIX Admin API: `http://localhost:9180`
- Internal service container port: `8000` (not published directly)

Run the React/Vite development server from `frontend/`. Run the backend from
`backend/` with `DATABASE_URL` configured. Do not assume the frontend is
connected to the gateway until that path has been tested.

## Security and Configuration

- Never commit passwords, API keys, tokens, or other secrets.
- Use environment variables for sensitive configuration.
- Do not expose development services publicly.
- Do not disable security checks merely to make tests pass.
- Review dependency vulnerabilities before deployment.

## Validation

For every meaningful change:

- Run the smallest relevant lint, build, or test command.
- Verify API responses and status codes.
- Check container logs when debugging Compose services.
- Test the actual request path through APISIX where applicable.
- Do not treat a successful build as proof that runtime behavior works.

## Git

- Preserve existing user changes.
- Do not reset, discard, or overwrite uncommitted work.
- Avoid destructive Git commands unless explicitly approved.
